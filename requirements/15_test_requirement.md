# テスト実装方針 (Test Implementation Policy)

## 1. 基本コンセプト
個人開発におけるスピードと保守性のバランスを重視し、**「壊れたら致命的なメインシナリオ」**に絞ってテストを実装する。網羅性よりも、回帰バグの防止と機能開発への時間割り当てを優先する。

## 2. E2Eテスト (Playwright)
**目的:** ユーザーの主要な操作フローが正常に動作することを確認し、リグレッション（先祖返り）を防ぐ。

- **実装範囲:** 1〜3本の「メインシナリオ」に厳選（計3〜10テスト程度）。
- **重点項目:** - ログイン → ダッシュボード表示
  - カード作成 → 学習実行
  - 復習日の更新（SRSロジックの反映確認）
- **方針:** 単純なUIの崩れよりも、画面遷移とデータの永続化を優先して検証する。

## 3. ユニット / コンポーネントテスト
**目的:** 複雑なロジックの正確性を担保し、リファクタリング時の安心感を得る。

- **実装範囲:** 必須ではない。以下の「計算・ロジック」のみに限定する。
- **重点項目:** - **SRS (間隔反復) アルゴリズム:** 次回の復習日計算など、境界値テストが必要な箇所。
  - **ビジネスロジック:** 条件分岐が複雑なユーティリティ関数。
- **方針:** UIコンポーネントのテストはE2Eで代替し、純粋な関数（Pure Functions）のテストに集中する。

## 4. 開発時の「割り切り」ルール
- **時間を機能開発に振る:** E2Eは最低限（1〜3シナリオ）とし、過剰なカバレッジは求めない。
- **UIテストの簡略化:** 見た目の微調整は手動確認で許容し、自動テストは機能の導通確認に徹する。
- **追加の判断基準:** 「その箇所を修正した際、影響範囲が予測しにくいか？」を基準に、複雑なロジックのみユニットテストを追加する。
