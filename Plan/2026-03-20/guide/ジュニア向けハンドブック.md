## 1. このアプリのデータが「どこにいるか」

| 場所 | 中身 | リロード | 別の PC / スマホ |
|------|------|----------|------------------|
| **SQLite（サーバー）** | デッキ・カードのテキスト、SRS 日付など | DB ファイルが残れば**残る** | 同じサーバー・同じユーザーなら**見える** |
| **IndexedDB（ブラウザ）** | 画像の実体（バイナリ） | ブラウザを消しても**基本残る** | **その端末のそのブラウザだけ** |
| **Zustand（メモリ）** | 画面が使うコピー | **リロードで空**になる → API で取り直す | 関係なし（そのタブの話） |

**リロード後に一覧が空に見える**とき、まず疑うのは「DB が消えた」ではなく、**メモリ上の Zustand がまだ空のまま**、または**空のまま再描画されていない**ことです。

### 1 知れば 10：「シングルソース・オブ・トゥルース」

- **本当のデータ**は DB（と IndexedDB の画像）。  
- **画面**はあくまで「今表示用に持っているコピー」。  
- バグを追うとき **「どのレイヤーが古い／空／更新されていないか」** を切り分けると、10 案件のうち 8 は早く終わります。

## 2. Zustand の `useStore(selector)` — 3 つの罠

### 罠①：メソッドだけを返す

```ts
// 悪い例：getDeck 関数の参照はずっと同じ
const getDeck = useDeckStore((s) => s.getDeck);
const deck = getDeck(id);
```

- セレクタの戻り値 = **いつも同じ関数オブジェクト**。  
- ストアの `decks` が変わっても **「選択結果が変わっていない」** → **再レンダーされない**。  
- 結果：**DataInitializer がデータを入れても画面が止まったまま**。

**直し方:** データに触れる参照を返す。

```ts
const decks = useDeckStore((s) => s.decks);
const deck = useMemo(() => decks.find((d) => d.id === id), [decks, id]);
```

### 罠②：セレクタの中で毎回 `filter` / `map` で新配列を返す

```ts
// 危険：呼ぶたびに新しい配列インスタンス
const cards = useCardStore((s) => s.cards.filter((c) => c.deckId === id));
```

- React 19 + `useSyncExternalStore` は **スナップショットの安定性**を厳しく見る。  
- **毎回別の配列** → 「キャッシュしろ」警告や無限ループの原因になりうる。

**直し方:** 配列はストアの **`cards` 参照そのもの**だけ購読し、**`useMemo`** で派生する（topics/03 参照）。

### 罠③：`useRef` で「fetch 済み」を永久に立てる

- Strict Mode で effect が二段実行されると、**1 回目で ref=true のまま**、2 回目が **何もしない**ことがある。  
- **「一度失敗したら永遠に再取得しない」** も起きうる。

**直し方:** 「永久フラグ」ではなく、**キャンセルフラグ + リトライ**、または **依存が変わったら再実行できる effect** にする。

### 1 知れば 10：`useSyncExternalStore` の考え方

- 外部ストア（Zustand）と React をつなぐとき、React は **「前回のスナップショットと同じか」** で更新を判断する。  
- **参照が安定しているか**・**意味的に同じなら同じ参照を返せるか**が、パフォーマンスと正しさの両方の鍵。  
- これは Redux・Jotai など **購読型**の状態管理で共通です。

## 3. CSS：なぜ `position: absolute` でボタンと重なるのか

- `absolute` の子は、親の**フロー上の高さ**をほぼ伸ばさない。  
- 親が `min-height: 300px` なら、レイアウト上は 300px 程度。  
- 中身が 800px でも **はみ出して描画**され、その下に置いたボタンと **重なる**。

**直し方の方向性:**

- **親に `overflow: auto` + 高さ制約（flex で残り領域）** を切る  
- または **absolute をやめたフリップ実装**に変える（大工事）

### 1 知れば 10：Flex で「残り全部スクロール」

- 縦 flex の子でスクロールさせたいとき、よく **`flex: 1`** と **`minHeight: 0`** のセットが必要。  
- `min-height: auto` のままだと **子が縮まず**、親がはみ出す・スクロールが効かないことがある。  
- **ダッシュボードのカード、モーダル内リスト、チャット UI** でも同じパターンが何度も出ます。

## 4. 今回の修正を「手順」として再現するなら

### 4.1 復習画面の重なり

1. DevTools でカードとボタンの DOM を見る。  
2. `.card-flip-front` が `absolute` か確認。  
3. 親の高さがコンテンツに追従していないことを確認。  
4. 外側に **`flex: 1` `minHeight: 0` `overflow-y: auto`** のラッパーを置く。  
5. ボタン行に **`flexShrink: 0`**。

### 4.2 プレビュー

1. 既存の `/review` に **クエリパラメータ**でモードを足す。  
2. そのモードでは **API で SRS を更新しない**ことをコードレビューで確認。  
3. 一覧からは **`router.push` で URL を組み立てる**だけ。

### 4.3 リロードで空

1. そのページが **SSR でデータを渡しているか**確認。渡していなければ **DataInitializer 頼み**。  
2. Zustand の行で **`(s) => s.getXxx` だけ**していないか grep。  
3. `filter` をセレクタに直書きしていないか確認 → **`useMemo` に逃がす**。

## 5. 画像が「スマホで登録したのに PC で見えない」について（予告）

これは **今回のバグとは別の構造**です。

- 画像は **IndexedDB** にあり、**そのブラウザプロファイルの中**だけ。  
- カードの `frontImageId` は **サーバーに保存**されるが、**画像バイト列はサーバーにない**（現状の設計）。  
- だから **別端末では ID だけあって画像が無い**状態になり得る。

**対応の方向性（残タスクで管理）：** 画像を **サーバー or オブジェクトストレージ**に上げる、または **同期付き KV** など。ARCHITECTURE の「画像は ID 参照」にも関わる大きめの変更です。

### 1 知れば 10：「クライアント専用ストレージ」の境界

- **localStorage / IndexedDB / Cache API** は「この origin のこのブラウザ」。  
- **ログインしたユーザーが同じ**でも、**端末が違えば別世界**。  
- 「ユーザー単位でデータを揃えたい」なら、**最終的にサーバー側に実体を持たせる**設計が必要、という判断が何度も効きます。
